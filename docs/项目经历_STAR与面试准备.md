# Vue 3 Schema 驱动低代码平台

Vue 3 + TypeScript + Vite + Element Plus + pnpm workspace · `[项目周期]`

面向表单和页面搭建。设计器把页面保存为 Schema，同一份 Schema 可交给 Runtime 预览，也可生成 Vue SFC。仓库目前拆成 7 个 workspace 包。

**核心贡献**

- 修复隐藏节点导致的拖拽落点错位：画布按 DOM 可见节点计算落点，但 Schema 的 `children` 仍包含隐藏节点，两个下标不能直接对应。改为传递 `beforeId`，由 `NodeTree` 回查 Schema 中的真实位置；`drop-at-bottom-appends` 用真实鼠标拖拽验证了 DOM 只有 2 个节点、Schema 有 3 个节点时仍能正确插入。
- 修复设计态误执行组件动作：渲染层此前无条件绑定事件，画布上点配置了 `navigate` 的按钮会改变页面 hash，`request` 等动作也可能产生副作用。改为仅在非设计态绑定节点事件；浏览器检查同时验证画布点击不执行、预览点击仍执行。
- 修复导出页面输入框无法填写：原先把 `modelValue` 生成为静态属性，用户输入后组件发出的新值没有回写位置，输入会被旧值覆盖。生成器现在输出 `v-model="formData.<nodeId>"`，并按 Schema 默认值初始化响应式 `formData`；集成测试编译并挂载生成页后实际输入，确认内容能保留。
- 将 Runtime 的节点查找从 `schema.nodes.find()` 改成构造时建立的 `Map` 索引，单次查找由 O(n) 降为 O(1)，整页节点查找由 O(n²) 降为 O(n)。以 500 节点、每次都扫完整数组的最坏情况估算，比较次数上界约为 25 万次，Map 查找为 500 次；这是复杂度估算，不是端到端耗时数据。

> 按实际分工调整“负责”范围。仓库没有线上使用规模或效率指标，未测量的数据不要补写成结果。

## 面试问答

### 1. 简单介绍一下项目，以及你负责什么。

这是一个 Vue 3 + TypeScript 的 Schema 驱动低代码平台。设计器编辑页面配置，Runtime 用这份配置生成预览，Codegen 则生成可继续开发的 Vue SFC。我实际负责 `[填写模块和职责]`。比较能说明工作内容的，是我处理过拖拽落点偏移、设计态误触发事件，以及生成页面无法输入这几类问题；它们都不是加一个配置项就能解决，需要把 DOM、Schema 和运行时行为对起来。

### 2. 隐藏节点为什么会让拖拽插错位置？怎么修的？

落点是根据浏览器里可见节点的矩形算出来的，但写回的是完整的 Schema 子节点列表。比如 DOM 里只有 `a`、`c`，Schema 顺序是 `a`、`hidden`、`c`，可见列表的下标 1 并不是 Schema 的下标 1。我让落点携带“插到哪个节点之前”的 `beforeId`，再由 `NodeTree` 查这个节点在完整 Schema 中的位置。回归检查既断言隐藏节点仍占 Schema 位置，也用真实鼠标拖拽验证最终顺序。

### 3. 为什么设计态要屏蔽节点事件？

用户在画布上点按钮，是要选中和编辑它，不是执行页面动作。之前 Runtime 不区分设计态和预览态，事件无条件绑定，所以点一下配置了 `navigate` 的按钮，编辑器的 hash 就会变化。现在只有非设计态才绑定节点事件。浏览器测试做了正反两组：画布点击不改变 hash，同一个按钮在预览里仍会触发动作，避免把事件功能一起关掉。

### 4. 导出的页面为什么不能输入？你怎么确认修好了？

生成器原先把 `modelValue` 当普通静态属性输出。输入组件虽然会发 `update:modelValue`，但父级没有用新值更新它，下一次渲染又把旧值传回来，所以输入留不住。我改成生成 `v-model`，并在 `<script setup>` 里生成以节点 id 为字段名的响应式 `formData`，初始值来自 Schema。测试不只检查输出字符串，还会编译并挂载生成页，输入文本后断言输入框里仍是新值。

### 5. 为什么既保留 Runtime 渲染，也做 Vue SFC 生成？

Runtime 用于拿到 Schema 后直接渲染，适合编辑器预览和动态页面；SFC 生成则让页面能脱离设计器，放进业务工程继续维护。两条路径读同一份 Schema，但实际渲染机制不同，功能容易不一致，所以我会把生成结果编译、挂载后测交互，而不是只断言输出里有某段模板字符串。输入框不能保留值的问题就是这样暴露出来的。

### 6. Runtime 的 `Map` 索引带来了什么变化？

递归渲染每个节点时都要按 id 找 `PageNode`。原实现每次从 `schema.nodes` 做线性查找，N 个节点反复查找，最坏查找量是 O(n²)；现在在 `RuntimeContext` 初始化时建好 `nodeMap`，之后每次按 id 取节点是 O(1)，整页节点查找为 O(n)。500 个节点时，按每次都扫完整数组的上界估算，是约 25 万次比较对 500 次 Map 查询。这个数字只描述查找复杂度，不等于页面总耗时提升了 500 倍；建索引也需要 O(n) 时间和空间。

### 7. 你怎么验证这几类问题不只是“代码看起来改对了”？

纯数据结构和状态规则用单测覆盖，比如 Schema 隐藏节点顺序和 `NodeTree` 的 `beforeId` 定位；生成代码用集成测试编译、挂载后真实输入；浏览器行为则用 CDP 驱动真实鼠标验证拖拽，并检查设计态与预览态点击的差异。因为 happy-dom 没有真实布局，也不能完整代替浏览器原生拖拽，所以拖拽只靠单测不够。
