# 五层架构企业级实践反推与基建优化（前端视角）

> 本文不是对《低代码平台架构设计：Schema驱动、渲染引擎与插件体系全解.md》的复述，而是**拿它的五层图反推「企业级实践到底该长什么样」**，再逐层对照本仓库真实代码，给出前端可落地的优化项。
>
> 结论先行：**那篇文章是"示意级"架构；你的仓库在 Schema 层已经超出它，但存在一个结构性错位——Schema 层（2.x 声明式）已先行，引擎层仍在跑 1.x 兼容视图。** 优化主线不是"照着文章补功能"，而是"让引擎层原生消费 2.x Schema，把声明式承诺兑现"。

## 一、用户交互层：设计器 = 运行时 + 编辑态壳

### 1.1 文章反推

文章把"可视化设计器 / 页面预览 / 应用管理 / 权限管理"并列成四个平级 UI。但企业级实践里它们**不是四个并列界面，而是两种运行模式 + 两个纵向能力**：

- **设计器与预览共用同一套渲染内核**，差异只在"是否注入编辑态 overlay（选中框/悬停/落点/标尺）"。文章 3.3 的 `DynamicRenderer` 正是这个意思，只是它把编辑态和运行态写成了两套东西。
- **应用管理**是"资源聚合 + 发布状态机"，不是简单的页面列表。
- **权限管理**贯穿所有层，不是交互层独占的一块面板。

### 1.2 你的现状

- `packages/runtime/src/renderer.ts` 的 `RuntimeRenderer` 已经通过 `wrapNode` 注入编辑态（`wrapNode?: (node, inner) => VNode`），`EditorEngine`（`packages/editor/src/engine/editor-engine.ts`）内部直接持有 `RuntimeContext`——**"共用内核 + 编辑态壳"这条最难的路你已经走对了**。
- 应用管理只有 `packages/playground/src/storage.ts` 的 localStorage 仓储，**没有"应用"聚合概念，也没有 draft/published 状态**。
- 权限：`DataModelPermissions` 三级模型已在 Schema 声明，但**前端没有任何消费端**（无 `can()`、无指令、无路由守卫）。

### 1.3 企业级实践 + 优化落点

1. **应用壳（Application Shell）**
   - 定义 `Application = { id, name, pages[], theme?, materialSet?, status: 'draft' | 'published', publishedVersion }`。
   - 页面发布 = 生成**不可变快照**（snapshot 与草稿分离），预览永远跑快照、编辑器永远跑草稿。这是企业级"发布/回滚"的最小模型，且全是前端可做的（快照存仓储）。
   - 落点：`packages/playground` 或新 `packages/app`，抽 `ApplicationStore`（Pinia）+ `ApplicationRepository`（见第五层）。

2. **权限消费端（纯前端等价物）**
   - 前端无法替代后端鉴权，但可以**消费**权限声明：`PermissionService { user, roles, can(resource, action) }`，把 `DataModelPermissions` 的三级（表/字段/操作）翻译成：
     - 菜单/路由级：`v-permission:read` / `router.beforeEach` 过滤；
     - 字段级：表单单字段 `hidden/readonly`（直接喂给表单引擎）；
     - 操作级：按钮禁用/隐藏。
   - 落点：`core` 加 `permission/`（纯函数，不碰 Vue），`playground` 注入假用户角色演示。

3. **设计器 UI 重建时的唯一入口约束**（已定原则，这里固化）
   - 新设计器只依赖 `EditorEngine` + `RuntimeRenderer` + `MaterialRegistry`，编辑态 overlay 作为**独立可替换层**挂在 `wrapNode` 上，不侵入 renderer。这条在 `docs/refactor-assessment.md` 已写，务必保持。

## 二、Schema 驱动层：声明先行，但要有"消费者"

### 2.1 文章反推

文章展示了页面/数据模型 Schema 各一段 JSON，但把"Schema 驱动"讲成了"数据用 JSON 存"。企业级实践里 Schema 驱动的核心不是"存 JSON"，而是**三件事**：

1. **单一事实来源（Single Source of Truth）**：页面不内联业务数据，而是 `ref` 引用外部契约（文章 2.2 里 `customerId → Customer` 是关系，但它的页面 Schema 里 `dataSource: { api: '/api/orders' }` 还是内联 URL——这是它没想清楚的地方）。
2. **Schema 即契约，双向生成**：数据模型 → 自动生成表单/表格/校验；API Schema → 自动生成请求封装 + 参数校验 + mock。否则"Schema 驱动"只是"JSON 换了个存放位置"。
3. **版本化 + 迁移链**：文章痛点 3 只说了"要兼容"，没给机制。真正的机制是"迁移注册表 + 链式迁移 + 边界归一化"。

### 2.2 你的现状（这一层你是超前的）

- `packages/schema/src/types/schema.ts`：统一信封 `SchemaEnvelope { version, kind, metadata, spec, migrations }`，五类 `Page/DataModel/Process/API/Plugin`。
- `packages/schema/src/types/pageSpec.ts`：页面数据源已经是**声明式引用**——`UnifiedDataSource` 的 `type: 'DataModel' | 'API'` + `ref`，而不是内联 URL。这一步你直接纠正了文章的错误。
- `packages/schema/src/types/action.ts`：动作已抽象成标准枚举 `UnifiedEventAction { type, target, params, expression }`，去掉了命令式 `children/catch/continueOnError`。
- `packages/schema/src/migration/registry.ts`：`MigrationRegistry` 用 BFS 找迁移路径，`migrateToUnified` 把 1.x → 2.x 并生成 `migrations` 记录。
- `packages/schema/src/validation/schema.zod.ts`：zod 校验五层信封 + semver。

### 2.3 差距（也是本文最重要的结构性发现）

**DataModel / Process / API / Plugin 四类 Schema 有声明、有校验，但没有一个引擎在消费它们。** 证据链：

- `normalize.ts` 第 51-62 行：`DataModel` 数据源被降级成 `type: 'rest'` + `config: { modelRef, operation, filter }`，注释（第 70 行）明写"实际取数语义由统一 DataSourceManager（DataModel/API ref 解析器）执行"——**这个解析器目前不存在**。
- `core/src/datasource/manager.ts` 的 `fetch` 只认 `static/rest/localStorage/sessionStorage/pageVariable`，没有 `DataModel/API` 分支。
- `normalize.ts` 第 103 行：`interactions` 被降级回旧 `rules`，`RuntimeContext`（`runtime/src/context.ts` 第 184 行）读的是 `this.schema.rules`——**运行时根本没在跑 2.x 的 `interactions`**。
- `action.ts` 的 `unifiedEventToLegacy` 第 60 行注释自己承认：`submit / refresh` 没有一等实现，被映射成 `custom` 动作，注释说"语义完整实现应由统一 Action 引擎提供"——**这个统一 Action 引擎目前没有**，`builtin.ts` 只有 7 个按旧 `kind` 注册的动作。

一句话：**Schema 层已经把"目标架构"画好了，引擎层还在用兼容垫片跑 1.x。** 这既是最大的技术债，也是最高性价比的优化点。

### 2.4 企业级实践 + 优化落点

1. **引用解析器（Reference Resolver）**
   - `core` 新增 `schema-registry/`：注册所有 DataModel/API/Process 信封，`resolveDataModel(id)` / `resolveApi(id)`。前端"数据库"就是这份注册表（后端可换成 REST 拉取，接口不变）。
   - `DataSourceManager` 增加 `DataModel/API` 取数分支：`DataModel ref + operation + filter` → 组装成对 CRUD 端点的调用（`/api/entities/{ref}?filter=...`），`API ref + params` → 按 `ApiSpec.endpoint/method/auth` 请求。
   - 收益：页面 Schema 彻底去内联，运行时才真正"Schema 驱动取数"。

2. **双向生成（把声明变成能力）**
   - `DataModel → 表单引擎输入`：`dataModelToFormSchema(model)` 生成字段列表（含 `FieldValidation` 映射到校验规则、`relation` 映射到下拉/子表）。
   - `DataModel → 表格列`：`dataModelToColumns(model)` 生成列定义（类型 → `tag/money/date` 渲染）。
   - `API → 请求封装 + mock + 参数校验`：由 `ApiSpec.request.params/query/body` 生成 zod 校验与 TypeScript 类型。
   - 这一条把"表单引擎/API 引擎"的前半段免费拿到了（见第三层）。

3. **统一迁移入口 + 迁移测试基建**
   - 现在只有 `migratePageSchema`（旧扁平）。补 `migrateEnvelope(input)`：读 `input.version` → BFS 找路径 → 链式迁移 → `parseSchema`。
   - 每个迁移写成**纯函数 + fixture 对测**（输入快照 → 输出快照 + 幂等性断言）。`migrations` 字段从"记录"升级为"可回放历史"。

4. **校验从 throw-only 升级为结构化报告**
   - zod `safeParse` 返回 `issues[]`（定位到 `path`），编辑器据此做**字段级红框 + 错误列表**，而不是一个 `throw` 顶死整个保存。

## 三、引擎层：让引擎原生消费 2.x Schema

这是五层里**投入产出比最高**的一层。文章列了五个引擎，你已有一个半（渲染●、规则●、API○），缺表单、流程，且规则/API/动作三处都在跑兼容视图。

### 3.1 渲染引擎（已有，做三个加固）

现状：`renderer.ts` 递归渲染 + `nodeMap` O(1) 查找 + `MAX_DEPTH=32` 防递归 + 单节点错误边界 + `EngineMetrics`。这是标准且扎实的做法（文章 3.3 的 `DynamicRenderer` 反而更粗糙）。

企业级加固点：

1. **节点级 Memo**：现在任一数据源/状态变化，Vue 响应式会让整棵树重新生成 VNode。给 `buildNode` 加 `shouldUpdate`（props/bindings/loop 依赖指纹）或按 `v-memo` 语义做子树跳过，大页面收益明显。
2. **异步组件 + Suspense**：`resolver.resolve` 目前同步返回组件。企业级要支持 `() => import()` 的懒加载（文章痛点 1 也点名了"组件懒加载"），resolver 返回异步时用 `defineAsyncComponent` + fallback 占位。
3. **虚拟滚动**：大表格/大列表是低代码第一性能杀手，物料层提供 `VirtualList/VirtualTable`，或渲染层内置对 `list` 型节点的窗口化。

### 3.2 表单引擎（缺，最高优先级补）

企业级表单引擎不是"一个动态表单组件"，而是**「数据模型 → 动态表单 → 校验 → 联动 → 提交」的完整闭环**，你已有全部积木：

- `DataModelField + FieldValidation`（字段 + 校验）→ 表单输入；
- `JexlExpressionEngine`（沙箱表达式）→ 字段联动/条件显隐；
- `RuleEngine + ActionChainRunner` → 联动动作执行；
- `DataSourceManager` → 提交/取数。

**落点：`core/form/`（纯 TS）**

```text
FormSchema（字段 + 布局 + 联动 + 校验，由 DataModel 或独立定义生成）
   ↓
FormEngine（value/errors/touched/dirty 状态机 + validate/submit/reset）
   ↓
runtime 的 FormRenderer 消费 FormEngine，字段控件来自 MaterialRegistry
```

关键抽象（都可从现有类型推导）：

- `FieldDefinition = { name, label, widget, validation, visible?(expr), disabled?(expr), options?(dsRef) }`；
- 联动 = `Rule`（你已经有的 `condition → actions`），作用域换成 `$form`；
- 提交 = `submit` 标准动作（`UnifiedEventAction.type: 'submit'` 已声明，但引擎没实现——在这里补上它的一等实现）。

### 3.3 流程引擎（缺，ProcessSchema 已就绪）

`process.ts` 已定义 `start/end/task/apiCall/dataModel/delay/condition` 六类节点 + 边，但没有执行器。前端视角的流程引擎包含：

1. **节点执行器**：每个 `ProcessNodeType` 一个 executor（`apiCall` → 调 API、`dataModel` → 读写模型、`delay` → sleep、`condition` → 表达式分流）。
2. **实例状态机**：`{ instanceId, processId, currentNodeIds, variables, status }`，`task` 节点的 `complete/reject/transfer` 驱动流转。
3. **网关**：当前 `condition` 是二分支，补 `parallel`（并行网关：会签）与 `inclusive`（或签）。`ProcessEdge.expression` 已是现成的分支条件。
4. **运行时上下文**：`$input / $output / $record / $user / $form`，复用表达式引擎的命名空间机制（`buildExpressionContext` 已示范了五级作用域）。

**落点：`core/process/`**：`ProcessExecutor`（解释执行，与渲染引擎同构——都是"消费 Schema 的递归解释器"）+ `runtime` 里一个 `ProcessViewer`（流程图 + 高亮当前节点）。

> 前端只管**编排与交互展示**，真正的审批持久化在后端；前端流程引擎的职责是"正确驱动状态机 + 正确渲染进度 + 正确把 task 表单喂给表单引擎"。边界划清即可，不必自建 BPMN 引擎。

### 3.4 规则引擎（已有，做一处关键纠正）

现状：`RuleEngine`（拓扑排序 + 防抖 + 重入保护 + timing）本身没问题。**问题是它消费的是 1.x `Rule`（`condition` 字段），而不是 2.x `interactions`。**

纠正：

1. `RuntimeContext.runRules` 改为消费 `UnifiedInteraction`（`expression` 字段），或让 `normalizePageSchema` 之后的运行时**直接持有 2.x 视图**，把旧 `Rule` 只保留给"读旧存档"的边界。
2. 触发粒度从"datasource 一变全跑"收紧为**字段级依赖**：`interactions.dependsOn` 已经是依赖声明的雏形，扩成 `dependsOn: ['$datasource.x', 'page.a']`，求值时按依赖快照判断是否真的需要重跑。

### 3.5 API 引擎（○ → ●，把"雏形"补成"引擎"）

`DataSourceManager` 已经是状态机雏形（loading/success/error + 轮询 + 失败隔离）。企业级 API 引擎要在其上补四块：

1. **ref 解析**（接 2.4-1）：`DataModel/API` 数据源真正取数，而不是靠 `normalize` 降级成 `rest`。
2. **编排**：数据源依赖（A 完成才取 B）、请求去重（同 key 并发合并）、缓存（TTL + 手动失效）、乐观更新（`setData` 已具备，补回滚）。
3. **统一响应契约**：`responseAdapter` 把 `{ code, data, message }` 归一成内部结构；`request` 生命周期钩子（认证注入 / 401 统一跳登录 / token 刷新 / 全局 loading）。
4. **Mock 与契约校验**：`ApiSpec.response.schema` 生成 mock 并校验响应结构——联调期无后端也能跑。

## 四、插件层：从"机制"到"打包单元 + 卸载 + 沙箱"

### 4.1 文章反推

文章 4.2 给了 `LowCodePlugin` 接口（组件/连接器/函数/面板/钩子），4.3 给了 `WeComConnector` 示例。它最值钱的一句是："允许第三方在不修改平台源码的情况下扩展功能"。企业级实践把这句话拆成三条硬约束：

1. **插件是"能力注册"，不是"代码混入"**——平台只暴露注册 API，插件不碰平台内部。
2. **插件是可分发的打包单元**——manifest + 版本 + 依赖 + 沙箱加载，而不是"往代码里塞个文件"。
3. **卸载与生命周期对等**——`install` 能做的，`uninstall` 必须能干净撤销。

### 4.2 你的现状

- `core/src/plugin/manager.ts`：`PluginManager + PluginAPI`（registerAction/registerMaterial/addFunction/emit），方向正确。
- `core/src/plugin/hooks.ts`：`HookBus` + 9 个生命周期钩子。
- `schema/src/types/plugin.ts`：`PluginSpec` 声明式描述（组件注册表/动作类型/表达式函数/入口）。
- `core/src/remote-material/loader.ts`：远程物料加载（ESM/UMD + 缓存 + 重试 + fallback）。

### 4.3 差距与落点

1. **连接器（Connector）补全**——文章 4.3 的 `WeComConnector` 可以前端化为：

```ts
// schema/types/connector.ts（新增）
interface ConnectorDefinition {
  name: string; baseUrl?: string;
  auth?: { type: 'bearer' | 'apiKey' | 'oauth2'; /* 配置项 Schema */ };
  actions: Array<{ name; method; path; requestSchema /* JSON Schema 用于生成参数表单 */ }>;
}
```

   配合 `ConnectorRegistry`（`core/connector/`）：`auth` 配置生成配置表单，`actions` 生成可调用的动作（注册进 `ActionRegistry`）。这样"自定义连接器"就从文章里的后端概念变成前端可落地的插件类型。

2. **插件打包单元 + 远程加载**：把 `PluginSpec` 扩成 `PluginManifest`（组件 + 函数 + 动作 + 连接器 + 面板的清单），复用 `RemoteMaterialLoader` 的加载/缓存/重试思路，做一个 `RemotePluginLoader`。**沙箱**：自定义函数/组件在 iframe（UI）或受限执行上下文（纯逻辑）里跑，避免全局污染（呼应文章痛点 2 的"自定义代码失控"）。

3. **卸载对等**：`PluginManager.register` 目前不返回 dispose，`HookBus.on` 返回的 off 没被 PluginManager 持有。补：`register → dispose`，`uninstall(pluginId)` 撤销它注册的所有 action/material/function/hook。

4. **扩展面板（designer extension）**：设计器暴露 `registerPanel/registerToolbar/registerInspectorSection` 扩展点，让插件往属性面板/工具栏/右键菜单里挂 UI。`PluginSpec` 里已有 `entry` 字段的占位，落到具体扩展点 API。

## 五、基础设施层：前端等价物也要"接口化 + 可替换 + 可观测"

文章把这层写成数据库/文件/队列/缓存/认证，是纯后端视角。你已经在前端做了正确等价映射（`DataBus`=MQ、`MemoryStorage/localStorage`=存储、`HttpClient`=注入）。企业级前端基建的补齐方向：

### 5.1 存储：`Repository<T>` 接口 + 校验 + 可替换

现状 `playground/storage.ts` 是 localStorage 直写、三个 key 各自为政、无校验（`refactor-assessment.md` 已点名）。落点：

```ts
interface Repository<T> {
  get(id: string): Promise<T | undefined>
  save(item: T): Promise<void>
  list(): Promise<T[]>
  remove(id: string): Promise<void>
}
```

- 读时用 `@lowcode/schema` 的 zod `safeParse` 校验（坏数据不进运行时）；
- 实现可换：`localStorageAdapter`（现状）/ `indexedDbAdapter`（大 schema）/ `restAdapter`（接真后端）。三者的差异只在实现，接口不动。

### 5.2 缓存分层

- **内存缓存**：已有（表达式 AST 缓存、远程物料缓存）。补：数据源响应 TTL 缓存。
- **持久缓存**：IndexedDB 存应用快照/物料，避免每次全量拉取。
- 统一一个 `Cache<T>` 抽象（`get/set/invalidate`），别让每个模块各自为政。

### 5.3 身份认证（前端等价物）

前端不存密码、不做鉴权判定，但要**承载会话**：

```ts
interface AuthProvider {
  getToken(): Promise<string | null>
  refresh(): Promise<string>
  onUnauthorized(cb: () => void): void
}
```

- `HttpClient` 装饰器：注入 token → 401 触发 refresh → 二次 401 跳登录；
- 路由守卫消费 `PermissionService`（见第一层）过滤菜单与路由；
- 落点：`playground` 用假 AuthProvider 演示，真实实现换成 OIDC/自定义。

### 5.4 可观测性（这是现代"基础设施"的真正含义）

你已经零散具备了 `EngineMetrics`（render/datasource/rules/event 计时）和 `ErrorCollector`（单点错误隔离 + `onError` 上报钩子）。收口成一条链：

```text
EngineMetrics（性能）  ──┐
ErrorCollector（错误） ──┼→ 统一 Telemetry 出口 → 上报（Sentry/自建/控制台）
RuntimeError（上下文） ──┘
```

补一个 `traceId/pageId/userId` 维度，让"500 个应用时设计器卡顿"这类文章痛点 1 的问题**可定位到具体页面/具体引擎**，而不是靠猜。

## 六、跨层原则（三条，比单层修修补补更重要）

1. **Schema 即代码 → 也要有工程化**：schema 的 lint/测试/CI 与代码同等对待。仓库目前有 `pnpm test/typecheck`，缺 ESLint/Prettier/CI（`refactor-assessment.md` 已列）。**迁移和校验器必须有测试**，否则"版本兼容"就是空话。

2. **两条执行路径要保持行为一致**：`runtime`（解释执行）与 `codegen`（编译执行）是同一个 Schema 的两种消费方式。`codegen/generator.ts` 的 `buildScript` 目前是字符串拼接，一旦表单/流程引擎落地，导出代码必须能复现运行时行为——这是"低代码 → Pro-Code 无缝过渡"（文章第八节）的技术前提。

3. **声明式优先，命令式只做逃生舱**：文章痛点 2 的"自定义代码失控"，解法不是禁用代码，而是**把自定义代码收敛到沙箱插件里**（版本化 + 类型约束 + 可卸载 + 可 review），并持续把高频自定义逻辑"下沉"成平台标准能力（`STANDARD_ACTION_TYPES` 扩列、新物料、新表达式函数）。

## 七、优先级路线图（P0 → P3）

> 与 `docs/refactor-assessment.md` 的"重构顺序"互补：那是"修实现"，这是"补能力"。

| 优先级 | 动作 | 对应层 | 一句话理由 |
| --- | --- | --- | --- |
| **P0** | 统一 Action 引擎：给 `submit/refresh` 一等实现，`builtin` 改按 `type` 注册 | 引擎层 | 消除 `action.ts` 里自己承认的"语义未实现"，是 2.x 落地的最小闭环 |
| **P0** | `SchemaRegistry` + `DataSourceManager` 支持 `DataModel/API` ref 取数 | Schema/引擎 | `normalize.ts` 注释里"应有但无"的解析器，让声明式取数真正生效 |
| **P1** | 表单引擎 `core/form`（DataModel → FormEngine） | 引擎层 | 补齐最大空白，且直接消费现有 DataModel/表达式/规则积木 |
| **P1** | 仓储接口化 + Zod 校验 + IndexedDB 适配 | 基础设施 | 替换 playground 的 localStorage 直写，是应用管理/发布的底座 |
| **P2** | 流程引擎 `core/process`（解释执行器 + 网关 + 状态机） | 引擎层 | ProcessSchema 已就绪，补执行器即可点亮 |
| **P2** | 连接器 `ConnectorDefinition` + `ConnectorRegistry` | 插件层 | 把文章 4.3 的企业微信连接器前端化为可落地的插件类型 |
| **P2** | `PermissionService` + `AuthProvider` + 路由/指令守卫 | 交互/基础 | 把已声明的三级权限变成可消费能力 |
| **P3** | 插件打包单元 + 远程加载 + 卸载对等 + 沙箱 | 插件层 | 扩展性从"机制"升级为"可分发生态" |
| **P3** | 渲染 Memo / 异步组件 / 虚拟滚动 | 引擎层 | 文章痛点 1 的性能债，在应用量上来前先布好 |
| **P3** | `migrateEnvelope` 统一入口 + 迁移 fixture 测试 + ESLint/CI | Schema/工程化 | 版本兼容与工程化兜底 |

**执行建议**：P0 两条合并做，因为它们共享同一个 `SchemaRegistry` 与"引擎原生消费 2.x"的主线——做完 P0，`interactions`/`UnifiedDataSource`/`UnifiedEventAction` 就从"声明存在"变成"运行时生效"，其余层都建立在这个基座上。
